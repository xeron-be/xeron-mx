# XeronMX Helm Chart

Official Helm chart for deploying XeronMX on Kubernetes.

XeronMX acts as an automated backup MX appliance. It queues incoming email during primary mail server outages in an encrypted spool, then forwards messages once the primary recovers.

> **Beta.** The chart renders, lints and produces a configuration the daemon loads (checked in CI). It has run on kind with cloud-provider-kind: install, a `LoadBalancer` Service given an external address, mail through it, the spool surviving the pod's deletion, delivery to a Postfix in the cluster, and `helm upgrade` rolling the pod onto new values with the data kept. It has not run behind a cloud provider's load balancer yet.
>
> **Check that your load balancer preserves the client address.** Behind cloud-provider-kind's load balancer, a proxy, every connection arrived from the load balancer's own address even with `externalTrafficPolicy: Local`. XeronMX then evaluates SPF, blocklists and per-source limits against that one address, and every `Received:` header names it. Use a load balancer that passes connections through at layer 4 (MetalLB, GCP and Azure network load balancers, AWS NLB with IP targets), or turn on the PROXY protocol on the balancer and list its addresses in `smtp.proxyProtocolTrusted`. Either way, check a received message's `Received:` header after installing.

## Prerequisites

- Kubernetes 1.25 or newer
- Helm 3.8 or newer
- A `ReadWriteOnce` storage class for persistent volumes
- Ingress controller (for the web administration panel)
- `cert-manager` (recommended for TLS certificates)

## Quick Start

Install the chart with your primary hostname:

```bash
helm install xeronmx ./deploy/helm/xeronmx \
  --set hostname=mx2.example.com \
  --set ui.ingress.enabled=true \
  --set ui.ingress.host=mx2.example.com \
  --set ui.baseURL=https://mx2.example.com
```

Once deployed, open `https://mx2.example.com` to complete the initial administrator setup.

### DNS Records

Publish the secondary MX record pointing to your ingress or SMTP LoadBalancer IP:

```dns
example.com.   IN  MX  10  mail.example.com.
example.com.   IN  MX  20  mx2.example.com.
```

Ensure `mx2.example.com` has a valid reverse DNS (PTR) record matching your outgoing public IP.

## Architecture

### Storage and StatefulSet

XeronMX runs as a `StatefulSet` rather than a standard `Deployment`. Each replica mounts an independent persistent volume through `volumeClaimTemplates`.

Because each pod runs a local SQLite database and an encrypted on-disk spool, sharing a single volume across multiple pods would corrupt the database. The StatefulSet guarantees dedicated `ReadWriteOnce` storage per pod, predictable network identities (`xeronmx-0`, `xeronmx-1`), and safe rolling updates.

### Network

The container process runs as non-root (UID 65532) and binds port 2525. The Kubernetes Service maps external port 25 to container port 2525, removing the need for `CAP_NET_BIND_SERVICE` or host-level sysctl modifications.

The SMTP LoadBalancer Service enables `externalTrafficPolicy: Local` by default to preserve original client source IPs. Without this, connections appear to originate from internal cluster nodes, breaking connection filtering, DNSBL checks, rate limiting, and audit logs.

### TLS Certificates

In Kubernetes, TLS is typically handled with `cert-manager`:

The web panel terminates TLS at the ingress controller through `ui.ingress.tls`.

For inbound SMTP STARTTLS on port 25, configure `smtp.tlsSecretName` to reference a TLS secret generated by cert-manager. The secret is mounted at `/etc/xeronmx/tls`. Without this secret, STARTTLS remains disabled and inbound mail is received unencrypted.

## High Availability and Clustering

To run a multi-node cluster:

```bash
helm upgrade xeronmx ./deploy/helm/xeronmx \
  --set replicaCount=3 \
  --set cluster.enabled=true \
  --set existingSecret=xeronmx-secrets
```

In a cluster setup, each node operates an independent spool (shared-nothing model). Upstream senders distribute traffic across all published MX hosts. When a primary server recovers, each backup node drains its own queue directly to the primary.

Nodes communicate via HTTPS peer gossip using the headless service (`service-headless.yaml`), authenticating requests with `XERONMX_CLUSTER_SECRET`. Enabling `cluster.syncConfig: true` causes follower replicas to automatically synchronize domain records and submission credentials from replica 0.

## Configuration Parameters

| Parameter | Default | Description |
| :--- | :--- | :--- |
| `hostname` | `mx2.example.com` | Public FQDN used in SMTP greetings and certificates |
| `replicaCount` | `1` | Number of StatefulSet replicas |
| `persistence.size` | `20Gi` | Persistent disk quota per replica |
| `persistence.storageClass` | `""` | StorageClass name for PVC dynamic provisioning |
| `smtp.containerPort` | `2525` | Internal port bound by the container |
| `smtp.service.type` | `LoadBalancer` | Service type for public SMTP intake |
| `smtp.tlsSecretName` | `""` | Kubernetes Secret containing `tls.crt` and `tls.key` for STARTTLS |
| `queue.minFreeDiskBytes` | `1073741824` | Disk guard ceiling (default: 1 GiB), returns SMTP 452 if low |
| `smtp.proxyProtocolTrusted` | `[]` | Load balancer addresses or CIDRs that send the PROXY protocol, so XeronMX sees senders' real addresses; required from them, ignored from everyone else |
| `smtp.senderAuth` | `true` | Check SPF, DKIM and an existing ARC chain on every accepted message (never refuses mail) |
| `queue.bounces` | `authenticated` | `authenticated` sends delivery status notifications only to senders proven by SPF or aligned DKIM; `off` never sends them |
| `maintenance.drain` | `false` | Start the node in drain mode (rejects SMTP with 421) |
| `clamav.enabled` | `false` | Enable ClamAV antivirus body scanning |
| `dnsbl.enabled` | `false` | Enable DNSBL real-time connection reputation checks |
| `ui.baseURL` | `""` | Canonical external URL for the web UI and OIDC redirects |
| `ui.ingress.enabled` | `false` | Enable Ingress resource for the admin UI |
| `cluster.enabled` | `false` | Enable multi-node peer gossip and monitoring |
| `existingSecret` | `""` | Name of pre-existing Secret containing sensitive keys |

## Operations and CLI Access

The container image is built `FROM scratch` without an interactive shell. The companion CLI binary `xeronmxctl` is included directly in the container:

```bash
# Check node status:
kubectl exec -it xeronmx-0 -- /xeronmxctl --url http://127.0.0.1:8080 --token xmx_... status

# Trigger maintenance drain:
kubectl exec -it xeronmx-0 -- /xeronmxctl --url http://127.0.0.1:8080 --token xmx_... drain --wait
```

## Upgrades and Lifecycle

Database schema migrations execute automatically during startup. Rolling updates of the StatefulSet occur sequentially pod by pod.

The chart sets `terminationGracePeriodSeconds` to 60 seconds by default, allowing active SMTP sessions to finish cleanly before pod termination.
